## Why

The repository currently **violates a spec that is still live**. `openspec/specs/environment-aware-analytics/spec.md` — never archived, never superseded — requires that a production build emit both the Plausible init script and a `https://analytics.140d.art/js/...` script tag. Commit `e2516b3` (31/07/2026) removed both while leaving the spec in place, so the only capability the frontend has for measuring its own traffic is specified and unimplemented.

The removed integration pointed at **Plausible Cloud** through a custom domain. The replacement is a **self-hosted Plausible Community Edition v3.2.1** instance running on the Mac mini M1 that already hosts the staging environment and Nginx Proxy Manager, reachable at the same subdomain. Self-hosting keeps visitor data on infrastructure we own — which is the substantive difference, and the one the cookie policy must state.

Analytics is the last remaining measurement gap after the production load hardening work: we know the render ceiling (25 req/s on detail pages) and we know the API is healthy, but we have no idea how many people actually reach the gallery or which artworks they open.

## What Changes

- Restore the two `<Script>` tags in `client/app/layout.js`, gated on the existing `IS_PROD` from `client/lib/env.js` — unchanged, already specified, already correct.
- Point the tracker at the self-hosted instance: `https://analytics.140d.art/js/pa-JOgfdmGauUrT5eiOHnIDj.js`, where `<ID>` is generated by our own instance and read from its installation screen.
- Restore `https://analytics.140d.art` to **both** `script-src` and `connect-src` in `client/next.config.js`. Two directives, not one: without `connect-src` the script loads and silently records nothing.
- Add a disclosure paragraph to `client/app/legal/politica-de-cookies/page.js` stating that the analytics is self-hosted and installs no cookies or persistent identifiers.
- **Terminate `analytics.140d.art` on the production EC2 and reverse-proxy it to the Mac mini** (`deploy/nginx/140d.art.conf`, sixth server block). This was a non-goal until verification proved it is the only way to deliver the visitor's IP to Plausible — see design.md.
- Document the instance, its topology and its operational blind spots in `CLAUDE.md`.

Analytics loads **without cookie consent**, deliberately. Plausible stores nothing on the terminal equipment, which places it outside art. 22.2 LSSI. Gating it behind the banner would discard every visitor who chooses "Solo las necesarias" — precisely the cost that choosing a cookieless analytics was meant to avoid.

## Layers Affected

- **Frontend only.** `client/app/layout.js`, `client/next.config.js`, `client/lib/env.js` (comment), `client/app/legal/politica-de-cookies/page.js`.
- **No backend change.** No controller, validator, route, middleware or service is touched.
- **No database schema change.** `api/config/database.js` is not involved.
- **Production nginx:** `deploy/nginx/140d.art.conf` gains a sixth server block plus a port-80 companion; `deploy/nginx/README.md` documents the manual DNS and certificate steps. `deploy/deploy.sh` needs no change — it already syncs that file, validates with `nginx -t` and restores on failure.
- **New external integration:** a self-hosted Plausible CE instance, outside this repository, reached by the visitor's browser through the production nginx.

## Capabilities

### Modified Capabilities

- `environment-aware-analytics`: the analytics requirement is re-satisfied against a self-hosted instance instead of Plausible Cloud; the CSP obligation and the consent-independence are made explicit, because both are silent failure modes that the original spec did not cover.
- `cookie-policy-page`: gains a disclosure requirement for the cookieless, self-hosted analytics.

### New Capabilities

None. Nothing here is a capability the project did not already specify.

## Non-goals

- **Serving the tracker from the `140d.art` origin itself** (true first-party, which is what defeats blocklists). Not possible without moving `BASE_URL`: the ingestion endpoint is baked into the generated script as `BASE_URL/api/event`, and `BASE_URL` also governs where the dashboard lives and the WebSocket CSWSH check. The EC2 proxy adopted here keeps the `analytics.140d.art` hostname and therefore does **not** address blockers; it addresses the visitor IP, which is the blocking problem.
- **A separate hostname for ingestion and another for the dashboard.** Same reason: one `BASE_URL`, one hostname. Splitting them leaves the dashboard serving pages while its LiveView socket is rejected by origin.
- **A `NEXT_PUBLIC_PLAUSIBLE_*` variable.** See design.md — for a build-time value it buys nothing and costs the four-place wiring ritual.
- **Analytics in preproduction.** `NEXT_PUBLIC_APP_ENV=preprod` already suppresses it and that behavior is unchanged.
- **Server-side events from `api/`** (purchases, bids, auction adjudications). Worth doing later; out of scope here.
- **A new consent category in the banner.** `CookieConsentContext`, the pre-paint bootstrap script and the banner are untouched.
- **Monitoring the instance's reachability.** A real gap, named in design.md, but it belongs with the wider monitoring work in `docs/monitorizacion.md`.
- **Backups of the Plausible instance.** Operational, outside this repository.

## Impact

- **Deploy coupling:** the tracker URL is embedded at build time, so a change requires rebuilding the client image — not a restart. Production deploy runs through `./deploy/deploy.sh`, whose nginx cache purge is mandatory and already handled.
- **Preproduction:** unaffected, provided the M1's root `.env` carries `NEXT_PUBLIC_APP_ENV=preprod`. If it does not, preprod would start reporting into production's numbers after its next **rebuild**.
- **Availability:** none. The tracker is `afterInteractive` and asynchronous; an unreachable instance costs data, never a visitor-facing failure.
- **Prerequisite, now satisfied:** the instance is installed and the site registered; the issued id is `pa-JOgfdmGauUrT5eiOHnIDj`.
- **Manual, one-off and ordered:** the Route53 record for `analytics.140d.art` moves from a CNAME at the router's DDNS to an A record at the EC2, and the existing multi-SAN certificate is expanded to cover the name. Both are documented in `deploy/nginx/README.md` and must happen before the tracker is deployed.
- **The residential IP stops being public.** Visitors resolve `analytics.140d.art` to the EC2; the home connection is reachable only from it.
