## Host Mobile Console for Agora Broadcasts (`events.allow_mobile_host_console`)

Three interchangeable host view modes — `full` (the pre-existing view, unchanged), `console` (a landscape operating panel) and `preview` (video only) — for running a conference or exhibition talk from a phone mounted on a tripod. Opt-in per event via the «Consola móvil del host» checkbox, which only appears with `provider='agora'` **and** `interaction_mode='broadcast'`. Attendees, LiveKit events and `meeting` mode are untouched.

* **The binding constraint is height, not width.** Chrome for Android in landscape leaves **~300 px CSS** with the address bar showing. The console must fit entirely in that, and stay usable at 640 × 280. Hence the layout priority: video at ~40 % of the width (the framing is set before going live), controls as ≥48 px touch cards in the rest. Halving the width instead drops the cards to ~40 px tall on exactly the hardest device. Only the card column may scroll — never the page, the header, the video or «Finalizar stream».
* **One hook, several presentations.** `useHostMediaControls` owns devices, effects, the mic/camera/screen toggles and ending the event, and is instantiated **once in `AgoraLiveRoom`**, above the mode switch. `AgoraHostControls`, `HostConsole` and the compact room's `CompactHostControls` render from it. In the compact layout the mode switcher is not a dark bar: it is the «Vista del host» entry of the «Más» sheet. Instantiating one per presentation would reset the virtual-background processor (2.1 MB of WASM) and re-enumerate devices on every mode change; copying the logic would be two truths that drift, the mistake `zoneResolver` documents.
* **The normal tree is hidden, never unmounted.** The mode wrapper is always mounted and only swaps `className` — the same trick `TheaterShell` documents, and for the same reason: moving `whiteboardElement` in the React tree destroys and rejoins the fastboard room, losing the writable session.
* **An Agora track plays in one container at a time.** While an overlay mode is active the normal tree renders **no** `AgoraVideo` (`hostTrack` is forced to `null`), because unmounting one instance calls `track.stop()` and would blank the other. Safe because `stop()` on a **local** track ends local playback only — publishing continues, which is what lets the video move between modes without the audience seeing a cut.
* **`fullscreenchange` does NOT exit the mode.** Deliberate divergence from `TheaterShell`, which closes on it: here that would eject the operator from their console mid-broadcast on an accidental system gesture. The event only syncs the re-enter button. `screen.orientation.lock('landscape')` is attempted **after** `requestFullscreen` resolves — Android only grants it inside fullscreen — and both failures are ignored.
* **The screen wake lock is NOT gated on this flag.** `useScreenWakeLock` mounts in every live host view, Agora and LiveKit alike: a screen that sleeps mid-event is a defect of the host view, not a missing console feature. **Since `live-event-mobile-layout` it also holds for attendees while there is something to watch** (remote video or content on an Agora stage, a video-format event playing): Agora plays remote video in muted `<video>` elements, which cannot be trusted to keep a phone's screen on. The old "attendees don't operate anything" exclusion was reverted on purpose (13/09/2026). It needs a secure context, re-acquires on `visibilitychange` → visible (the browser releases it when the page hides), and degrades silently — a predictable browser refusal is not an application exception, so it never reaches Sentry.
* **Two controls the target browser cannot provide, shown disabled with their reason rather than hidden** (an empty gap reads as a failed load): screen sharing (`getDisplayMedia` is «device- and version-dependent; not reliable» on Chrome for Android — feature-detected, and a failure of the call is painted inside the card) and speaker selection (`setSinkId` and `audiooutput` enumeration are desktop-only; Android routes output itself).
* **Nothing inside the console may render through a portal to `document.body`.** The shared `ConfirmDialog` is built on Headless UI's `Dialog`, which does exactly that, and it failed twice over: the portal lands **outside the element in native fullscreen** (the browser paints only that subtree) *and* its `z-50` loses to the overlay's `z-[60]`. The symptom was a «Finalizar stream» button that did nothing at all and showed no dialog. The console therefore owns its own confirmation (`ConsoleConfirm`) and its own device picker, both plain children of the overlay — the same reason `MobileDevicePicker` exists rather than reusing `DeviceDropdown`. Any new UI the console needs follows that rule.
* **No API hides the address bar in a normal tab.** Native fullscreen recovers it while it lasts; `dvh` sizing plus a non-scrolling overlay stop the layout jumping. The most reliable route needs no code at all — **installing the site from «Añadir a pantalla de inicio»**, since `client/app/manifest.json` already declares `display: standalone`, leaves no address bar and no gesture that brings one back. That is the recommended procedure for a planned event.
* **Known blind spot:** the console's layout, the mic meter and the fullscreen behaviour have **no automated test** — `client/` still has no test runner. The API half (both columns, validators, persistence) is covered by `api/tests/eventHostFlags.test.js`, which runs the same six cases over each flag and asserts the four-place write path by name.
